# 报修闭环顾问 Agent 方案（RAG 驱动）— v2.0

> 版本：v2.0（范围已按业务确认校准，2026-08-20）  
> 日期：2026-08-20  
> 状态：✅ 已实施完成（2026-08-20，分支 `feature/rag-qa-agent`，任务 1-8 全部落 地，295 项测试通过）  
> 核心转变：**从「用户提问的问答机器人」改为「挂在工单生命周期上的闭环顾问」**——Agent 不等用户提问，而是在报修事件发生后主动参与：记录 → 建议 → 反馈 → 升级。  
> v1.0 的检索底座研究结论全部保留（附录 A）；`#问` 显式问答入口降为二期可选（附录 B）。

---

## 一、定位：事件驱动，而非提问驱动

v1.0 问答方案的最大风险是意图边界（「帮我修」vs「什么原因」只差几个字）。闭环顾问由**确定性生命周期事件触发**（建单、反馈、升级），模型永远不需要判断"该不该说话"——管道告诉它什么时候说话。这一转变同时消解了冷启动焦虑：不再要求第一天就有好答案，只要求系统越跑越好。

```
报修消息
  → ① 记录（v4.1 已建成，零改动）
  → ② Agent 主动建议（核心增量：RAG 检索相似历史工单，群公开+@工程师）
  → ③ 收集反馈（「解决了」→ 完单，零新增；「未解决」→ 升级，新增）
  → ④ 事态升级（AI 建议未解决 → 工程师接手；静默场景由既有时效机制兜底）
  → 工单完结 → 自动沉淀为新案例 → 案例库自增强
```

---

## 二、已确认决策（2026-08-20 业务确认）

1. **触发方式**：事件驱动（建单即建议）；`#问` 显式问答入口降为二期可选。
2. **建议可见性**：群内公开 + @工程师（透明且零额外机制）。
3. **升级定义**：**Agent 给出的建议解决不了问题 → 需要工程师解决**。由显式「未解决」反馈触发；用户无反馈的静默场景由既有 1/3/7 天 SLA 与责任周期提醒兜底（已建成）。
4. **范围口径**：报修信息（非"保修期"判断）。如后续需要保修期判断，可作为建议的一个字段（需设备台账），与本方案不冲突。
5. **建议不做人工复核**：直接发群；质量靠台账统计与复盘（复核会重新引入人工，与自动化目标矛盾）。
6. **自助完单记录口径**：无需工程师补录确认，Agent 建议直接记录为该工单的故障判断/维修方式（来源标记 `AI_SUGGESTION`）；「解决了」反馈即结果级验证。

## 三、闭环设计

### 3.1 记录 —— 已建成，零改动

v4.1 全套管道即此能力：建单、字段抽取、图片归档与视觉解析、诊断版本、维修方式版本、订单协作。结构化记录恰是检索质量的根基。Agent 只挂接在事件之后，不改动任何既有路径。

### 3.2 建议 —— 核心增量

**触发点**：建单事务提交、建单回执经 Outbox 发出后，异步触发建议任务。不进建单事务、不阻塞监听——建议是增值能力，不是依赖。

**检索**：查询文本 = 主题+设备+位置+故障描述 模板化拼接 → 混合检索（FTS5 + 向量 + RRF，见附录 A）→ 相关度 top-1 ≥ 阈值才发建议，低于阈值保持沉默（宁可不建议，不错误引导）。

**消息格式**（群公开 + @工程师，Outbox 顺序：建单回执在前、建议在后）：

```
💡 工单 W-xxxx 相似案例参考 @聂宇清
【现象匹配】冷柜不制冷、压缩机有嗡嗡声（历史 3 例相似）
【可能原因】制冷剂泄漏（2例）/ 冷凝器积灰（1例）
【历史处理】补充制冷剂 + 清洗冷凝器，当天恢复
【参考工单】W-2024-0131、W-2024-0098
如按建议恢复，回复「解决了」；仍异常请回复「未解决」，将请工程师处理
—— 基于历史工单，仅供参考
```

**台账**：每次建议落 `ticket_suggestions`（检索命中、分数、内容），支持事后统计命中率。

**降级**：模型或嵌入服务不可用 → 建议链路静默跳过并记日志，工单链路完全无感（呼应"关键词快路径"哲学）。

### 3.3 反馈

- **正向反馈（近零新增）**：「解决了 / 正常了 / 搞定了」早已在 `ticket.complete` 语义范围；且代码现状 `_execute_complete` 仅做 CAS 状态变更，**不强制先有故障判断**（README 描述的完成校验与代码现状有出入，以代码为准，实施时补集成测试固化）→ 自助完单路径畅通。
- **建议自动落档（2026-08-20 确认）**：自助完单时**无需工程师确认**，系统直接把 Agent 建议的原因+处理写入该工单的故障判断与维修方式版本表（`actor=AI`、来源标记 `AI_SUGGESTION`）。「解决了」即结果级验证——用户按建议操作后问题消失，证据强度不低于工程师猜测式诊断；且 schema 保持统一（完单工单均有诊断/维修方式记录，报表口径一致）。此类工单照常沉淀为案例，metadata 标注 `source=ai_confirmed_by_outcome` 供检索排序参考。
- **负向反馈（新增）**：`#未解决` 显式关键词 + 语义表达（还是不行 / 没修好 / 建议没用 / 更严重了）→ 触发升级。仅在已发过建议的工单上识别，避免误伤普通补充消息。
- **隐式比对（零打扰）**：工程师提交 `#故障判断` 时，系统自动比对"建议原因 vs 实际诊断"，命中/偏差落库——持续校准案例库排序，不需要任何人多打一个字。

### 3.4 升级 —— AI 未解决 → 工程师接手

**触发**：
1. 显式：用户回复「未解决」（立即升级）；
2. 静默：用户不反馈 → 既有 SLA 到期提醒与责任周期机制照常兜底（已建成，零新增）。

**动作**：
- 工单打 `ai_escalated` 标记 + 记录升级时间；
- Outbox 强提醒 @工程师（是否叠加工程负责人，对齐既有 4 小时升级接收人，实施时核实 scheduler 后定）；
- 升级消息带上下文摘要：故障描述 + 已给建议 + 「未解决」反馈原文，工程师不必翻聊天记录；
- **升级后该工单 AI 静默**：不再发建议、不再追问反馈（已证明无效，避免打扰）。

**与既有机制的关系**：时间维度（SLA/责任周期，已有）+ 事态维度（AI 未解决，本次新增）互补，不替换；升级不改变工单状态机（仍走 ACTIVE→COMPLETED），只是标记+通知，不触碰协议动作权限。

## 四、与既有系统的接缝（可行性关键）

| 接缝 | 结论 |
|---|---|
| 挂接点 | pipeline 建单 RESULT_OK 后异步任务；不进事务、不阻塞监听 |
| 通知 | 复用 notifier Outbox；回执→建议顺序天然保证 |
| 完单 | 「解决了」→ ticket.complete 现有链路即可，无需放宽校验 |
| 升级 | 只加标记列+通知，不动状态机与协议权限 |
| 失败隔离 | 建议/检索/嵌入任一失败 → 静默跳过；工单链路零影响 |
| 审计 | 建议台账 + 反馈记录 + semantic_decisions 既有审计表 |

```sql

CREATE TABLE kb_documents (...);          -- doc_id/source_type/title/content/content_hash/metadata

-- 建议台账（新增）
CREATE TABLE IF NOT EXISTS ticket_suggestions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ticket_id INTEGER NOT NULL,
  doc_ids TEXT NOT NULL,                  -- 命中的 kb_documents doc_id 列表 JSON
  top_score REAL NOT NULL,
  content TEXT NOT NULL,                  -- 发给群的建议原文
  feedback TEXT,                          -- RESOLVED / UNRESOLVED（显式）；隐式比对单独记
  created_at TEXT NOT NULL,
  escalated_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_sugg_ticket ON ticket_suggestions(ticket_id);

-- 工单升级标记（幂等 ALTER）
ALTER TABLE tickets ADD COLUMN ai_escalated INTEGER NOT NULL DEFAULT 0;
```

## 七、评测指标与灰度

**四项核心指标**（月度可量化价值证明）：
- 建议覆盖率 = 发出建议的工单 / 总建单
- 自助解决率（deflection）= 反馈「解决了」完单且工程师未上门 / 发出建议的工单
- 升级率 = 「未解决」升级 / 发出建议的工单
- 隐式命中率 = 工程师诊断与建议原因吻合 / 已有诊断的建议工单

**灰度**：SHADOW（只记台账不发群）→ 白名单群（group-test）→ 全量。

## 附录 A：检索底座技术选型（v1.0 结论，保留）

- **向量存储**：sqlite-vec（vec0 虚表）——与「SQLite 唯一真相源」一致、零独立服务；纯 numpy 余弦作降级路径；不引入 Chroma/Qdrant/FAISS（单进程部署过重）。50 群 × 数千文档/年规模绰绰有余。
- **Embedding**：OpenAI 兼容 `/embeddings` 端点，复用 `LLM_BASE_URL` 同款供应商机制；环境变量 `EMBEDDING_BASE_URL / EMBEDDING_API_KEY / EMBEDDING_MODEL`（如 bge-m3、text-embedding-3-small）。本地 sentence-transformers 仅作离线备选（torch 依赖过重）。
- **检索策略**：FTS5（trigram tokenizer，中文子串匹配，无需 jieba）+ 向量 KNN → RRF 融合 top-K。设备名精确命中靠 FTS，口语化描述靠向量；rerank 留二期。
- **生成**：复用 `OpenAICompatibleModelClient` 新增 `complete_text()`；单次调用、不内部重试、Inbox Worker 统一重试约束不变。
- **框架取舍**：不引入 LangChain/LlamaIndex；所需能力约 300~500 行自研，与「确定性规则内核、轻依赖」风格一致。
- **语料**：终态成功工单（一张=一篇案例文档，模板固定"现象→原因→处理"结构）+ 业务文档按标题切块 + 可选 FAQ；content_hash 变更检测增量重嵌入；模型/维度切换后 `--rebuild` 全量重建。
