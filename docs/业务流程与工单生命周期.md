# 钉钉群报修工单系统 · 业务流程与工单生命周期

> 更新：2026-08-12（新流程）· 版本 v4.0

本文档专注两件事：**一条群消息进来后系统怎么处理**、**一张工单从生到死怎么流转**。系统全貌见 `系统说明与淘宝对账协作.md`。

---

## 一、消息处理流程

### 1.1 总览

```
钉钉群消息
  │  dws event +listen-im 监听（每群一个进程，断线自动重连）
  ▼
标准化 + 角色识别（店长/工程师/其他成员/系统账号）
  │  系统账号（工程部AI）回流自动过滤
  ▼
收件箱入队 inbox_messages（幂等：同一条消息只入队一次）
  │
  ▼
Inbox Worker ── 跨群并行、群内按 (sent_at, message_id) 串行 ──
  │
  ├─ ① 待确认回复？  （确认/拒绝/修正 已有待办动作）
  ├─ ② 语义识别      关键词快路径（本地） 或  云端模型（受协议约束）
  ├─ ③ 语义决策审计   落库 semantic_decisions
  ├─ ④ 多工单路由     归属到具体工单
  ├─ ⑤ 校验          角色/必填字段/枚举/工单状态/版本
  ├─ ⑥ 待确认 or 执行 一个短事务（唯一执行记录 + 业务变更 + 归属 + 通知）
  └─ ⑦ 群通知        Outbox 异步发送
```

### 1.2 分阶段明细（按一条消息跟踪）

| 阶段 | 发生什么 | 可能结局 |
|---|---|---|
| **标准化** | NDJSON 事件 → 统一结构；缺字段/时间非法 → 丢弃 | 丢弃 / 进入收件箱 |
| **入箱** | `inbox_messages` 写入；message_id 重复 → 跳过 | RECEIVED |
| **待确认回复** | 该用户有 WAITING 待办时，识别「确认/拒绝/修正」 | 执行 / 取消 / 修正后执行 |
| **语义识别** | 关键词快路径（`#报修` 等）优先；否则云端模型 | 关键词 / 模型决策 / 模型降级 |
| **模型降级** | 模型超时/失败 → 退避重试 `[2s,10s]`，3 次后死信 | RETRY_PENDING → DEAD_LETTER |
| **路由** | 编号 > 引用 > 用户30分钟上下文 > 语义top1 > 单候选 | ROUTED / CLARIFY / CREATE |
| **校验** | 角色、必填字段、枚举、工单状态、乐观版本 | AUTO_EXECUTE / WAITING_CONFIRMATION / VALIDATION_REJECTED / IGNORE |
| **执行** | 一个事务：唯一执行记录 → CAS 业务变更 → 消息归属 → 幂等台账 → 通知 | OK / REJECTED(版本冲突) / INTERNAL_ERROR |
| **收尾** | 收件箱置 COMPLETED，发群回执 | COMPLETED |

### 1.3 每种结局对群里的表现

| 结局 | 群里看到 |
|---|---|
| 执行成功 | 建单/记录/完成等回执（如「✅ 已创建工单：…」） |
| 校验拒绝 | 「无法执行：缺少必填字段… / 角色…无权限…」 |
| 待确认 | 「确认执行：ticket.cancel（…）？回复「确认」继续」 |
| 多工单歧义 | 列出候选工单，请选择或提供编号 |
| 模型降级重试 | 群内无动作（后台重试） |
| 死信 | 「智能识别暂时不可用，本条消息未执行，请使用标准关键词」 |

## 二、工单生命周期

### 2.1 状态机

```
                        ┌──────────────────────────┐
                        │        ACTIVE            │ 处理中
                        │  （含自动延期、订单登记）    │
                        └──────┬───────┬───────────┘
           ┌──── 报修建单 ──────┘       │
           │                          │
           ▼                          ├── 提交订单号 → 自动延期 +3 天
      【ACTIVE】                       │
           │                          ├── 时效临近 → 群提醒（不切状态）
           │                          │
           ├── 回复「修好了」 ───────────► 【COMPLETED】 ✅ 完成（终态）
           │                             │
           └── 取消（需确认）────────────► 【CANCELLED】 取消（终态）
                                           │
                                           └── #重开工单 ──► 【ACTIVE】（reopen_count+1）
```

### 2.2 状态定义（当前实际）

| 状态 | 含义 | 是否终态 | 当前是否自动切换 |
|---|---|---|---|
| `ACTIVE` | 处理中 | 否 | ✅ 建单时进入 |
| `COMPLETED` | 已完成 | 是 | ✅ 回复「修好了」/`#完毕` |
| `CANCELLED` | 已取消 | 是 | ✅ 取消确认后 |
| `ACTIVE_OVERDUE` | 已超时 | 否 | ⚠️ 协议允许，但当前**不会自动切换**（SLA 提醒只通知、不改状态，是 Task 10 待做项） |

### 2.3 各动作如何改变工单

| 动作 | 触发 | 工单变化 |
|---|---|---|
| 建单 | `#报修` / 自然语言 | 新建 ACTIVE；编号 `店名-主题-时效-序号`；时效缺省 1 天 |
| 补充 | `#补充` / 自然语言 | 追加问题描述；版本 +1 |
| 故障判断 | `#故障判断` / 自然语言 | 写入 diagnosis_versions（留版本历史） |
| 维修方式 + 订单号 | `#维修方式` / 自然语言 | 写入 repair_method_versions；**若带订单号 → 自动延期 +3 天 + 登记共享表** |
| 超时原因 | `#超时原因` | 写入 timeout_cycles（当前仅记录，不自动延期） |
| 完成 | 「修好了」/`#完毕` | ACTIVE → COMPLETED（直接完成，无需确认） |
| 取消 | `#取消工单` / 自然语言 | ACTIVE → CANCELLED（**需确认**） |
| 重开 | `#重开工单` | COMPLETED/CANCELLED → ACTIVE（reopen_count +1，**需确认**） |
| 查询 | `#查询工单` | 只读，列活动工单 |
| 选择 | `#选择工单` | 建立该用户 30 分钟上下文，不改变工单 |

### 2.4 工单关键字段

- **编号**：`店名-主题-时效-序号`（如 `钉钉消息测试-博物馆-3天-001`），序号每群独立递增
- **`version`（乐观锁）**：每次业务变更 +1；并发冲突时 CAS 更新失败 → 拒绝并提示，不覆盖他人更新
- **截止时间**：创建时 = 建单时间 + 时效；提交订单号时自动 +3 天
- **`reopen_count`**：重开次数；**`cancelled_at/by/reason`**：取消留痕
- 诊断/维修方式都有**版本历史**（`is_current=1` 标记当前值）

## 三、关键机制

### 3.1 多工单并行与路由

- **同群可同时存在多张活动工单**（v4 已删除"每群一张"限制）
- 消息归属按 **5 级优先级**：明确编号 > 钉钉引用 > 用户 30 分钟上下文（`#选择工单`）> 语义评分 top1（≥0.90 且分差≥0.15）> 单候选兜底
- **歧义不猜**：多候选且无信号 → 回群列出候选，让用户选或提供编号

### 3.2 待确认动作（高危防护）

取消/重开/模型高置信动作 → 建 WAITING 待确认 → 群内问「确认？」：
- 用户「确认」→ 再次校验工单版本未变 → 执行
- 用户「拒绝」→ 取消；30 分钟未回 → EXPIRED
- 同一 (群,用户) 至多一个待办，新动作自动覆盖旧的

### 3.3 订单监控（淘宝采购协作）

```
提交订单号 → 工单自动延期 +3 天（每单一次）
         → 写入共享表 订单门店状态表.xlsx（order_id/store/ticket_no）
         → 另一个 AI 每天回传 status/tracking
系统读共享表，状态变化时群内通知一次：
  · 卖家已发货 → 提醒「已发货，留意收货」
  · 交易关闭   → 提醒「订单因未付款已关闭」
```

### 3.4 SLA 时效提醒

- 活动工单时效**前 6 小时** → 群提醒一次「时效即将到期，如已修复请回复「修好了」」
- **已超时** → 再提醒一次
- 去重：同一工单同一截止只提醒一次；已完成/已取消不提醒

### 3.5 并发与幂等

- **跨群并行、群内串行**：某群慢模型不阻塞其他群；同群按顺序处理
- **事务型 Outbox**：业务变更与通知预写同事务，提交后异步发送
- **乐观版本**：所有写工单都带 `version` 条件，冲突即拒
- **幂等三层**：收件箱 message_id 主键 / 幂等台账 processed_events / 执行记录 action_executions

## 五、当前边界（诚实说明）

- `ACTIVE_OVERDUE` 状态不会自动切换（SLA 只提醒），超时归属/升级逻辑未接
- 图片识别未做；报修表格导出未写；4 小时未回复升级未接
- 模型端点延迟高（create 类 ~35s），关键词快路径不受影响
